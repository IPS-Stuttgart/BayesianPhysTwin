# Deform360 pairwise regret-guard fresh technical lock v1

## Purpose

The source-qualified pairwise regret guard improves the selected
physical/persistence backbone on the opened Deform360 development panel, but
that result is not independent confirmation. This lock prepares the strongest
remaining public-data test without reusing a physical object that any local
study opened, reserved, selected, or technically dispositioned.

The result is necessarily a **technical replication**, not a state-of-the-art
claim. The public Deform360 catalog snapshot contains 190 physical objects.
The conservative union of all valid local exclusion manifests covers 189 of
them, leaving one untouched public object.

## Frozen method

The runtime method is unchanged from commit
`fc2ff43f2e100ce910bf8085a7e9e0144d87bae8`:

- select the physical rollout or exact persistence from prefix evidence;
- construct the unchanged pairwise-consensus RBF camera candidate;
- require action-conditioned physical and observed response;
- cap correction RMS relative to the physical response;
- admit only intervals inside source feature support with a strictly negative
  source regret upper bound; and
- return the selected baseline bit-for-bit otherwise.

The source protocol file SHA-256 is
`e00cdb8ea92b7f501054dcbd44a011019ec9b75001825c0bc523af9831fc7e9b`.

## Execution boundary

The execution order is frozen:

1. verify raw metadata, required streams, camera panels, synchronization, and
   source checksums;
2. process all nine valid episodes and check the 128-node physical-backend
   minimum before prediction;
3. construct prefix-only camera measurements and physical rollouts;
4. create an ordinary success or retained technical-failure seal for each of
   the nine episodes;
5. require all nine ordinary predictions, not merely nine terminal
   dispositions, before opening any future object trajectory;
6. score the selected baseline and frozen guarded update without refitting;
7. report every episode and failure, with no replacement.

The primary metrics are post-update hidden-identity RMSE and post-update hidden
symmetric Chamfer. Results are aggregated equally across update intervals and
then equally across the nine valid episodes. Admission count, exact-fallback
count, beneficial/harmful intervals, and technical failures are reported
separately.

No future camera or object observation may enter prediction. Known future robot
actions may condition the physical rollout, as in the frozen source protocol.

## Claim boundary

This evaluation can answer only:

> Does the frozen source-qualified guarded update transfer across multiple
> actions on the sole untouched public Deform360 physical object?

It cannot establish multi-object transfer, official Deform360 parity,
calibrated non-regression, or a state-of-the-art result. A positive technical
replication would justify moving the unchanged method to an independent public
dataset or newly released Deform360 objects. A negative result closes this
camera-update route under its current admission and regret certificate.
